# DevManager orchestration specifications

Status: LOCKED SPEC + COMPLETE BUILD PACK — 2026-09-12.

This is the repository's `/spec/` directory. It captures Robin's requested direction: give a lead software goals and rules, then have it investigate, plan, choose agents, implement, audit, test, repair, and independently verify complete outcomes. Inputs include finished specs, project briefs, slow pages, and failing-test campaigns. Command maintenance/features are the primary workload; DevManager and other projects are supported. Separate task leads share scoped project/user memory and host scheduling, and improve rules/process through evidence-based consolidation.

Read in this order:

1. [CONTEXT-PACK.md](CONTEXT-PACK.md) — inspected DevManager code, existing constraints, command sources, and verification limitations.
2. [ai-orchestration/SPEC.md](ai-orchestration/SPEC.md) — the product agreement, behaviors, scope, decisions, and observable acceptance scenarios.
3. [ai-orchestration/UX-SPEC.md](ai-orchestration/UX-SPEC.md) — the concrete native screens, actions, state coverage, feature-to-surface map, and linked visual targets. This is part of the SPEC.
4. [ai-orchestration/build/00-overview.md](ai-orchestration/build/00-overview.md) — exact interfaces, all 17 phases, 197-scenario coverage and native delivery gates; follow with each phase and TEST-PLAN.
5. [ai-orchestration/AUTONOMY-REVIEW.md](ai-orchestration/AUTONOMY-REVIEW.md) — reviewed scope gaps, settled policy amendments, and outstanding implementation proof.

There is one feature specification because the complete workflow is the first product outcome. The build pack splits it into 17 implementation phases with complete vertical slices. Separate provider, scheduler, and dashboard feature specs would make it too easy to finish infrastructure without delivering that outcome.
