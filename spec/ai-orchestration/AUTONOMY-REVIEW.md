## Settled policy amendments

### P1 — Lead-owned recovery after repeated failures

The old example required human escalation when a finding survived two fix rounds. A2 replaces that default for this workflow:

1. Perform up to two ordinary repair attempts for the finding.
2. If it remains open, obtain fresh diagnosis from an eligible session independent of those failed repairs.
3. The lead may choose up to two further materially different repairs, each with independent verification.
4. If still unresolved, preserve the diagnosis/evidence and expose a precise blocker while independent work continues.

The default is four completed repair attempts per unresolved finding/cause, not four repairs for an entire project or campaign. Grouped symptoms of the same persistent cause cannot each gain a new allowance. A stricter explicit user budget can stop admission sooner; an explicitly selected project recovery policy can choose a different finite limit. Incomplete verification is recovered under bounded process/environment rules. Counts survive restart, regrouping, and profile changes; renaming a finding cannot reset them.

Product changes, acceptance changes, unauthorized actions, and exhausted authority still reach the user. This policy does not kill an in-flight productive compiler when the next-attempt limit is reached, accept unverifiable output, or permit an endless loop with fresh labels.

P1 is adopted in SPEC A2 and reflected in A05–A07.

### P2 — Owned disposable test-environment authority

Amendment A2 adds a standing grant to create, prepare, migrate, seed, restart, and reset explicitly owned disposable test resources required for the feature. The lead uses actual project commands, approved sources, and existing account/budget authority. This removes the repeated manual setup handoff before E2E.

Ownership is established from the actual resource created or explicitly assigned to the run. A “test” name, localhost address, or environment-variable label alone is insufficient. Verify the real connection target and preserve isolation from existing shared and production resources. A separate explicit restriction on the actual environment remains binding.

Production migrations, existing shared development databases, production-data copying, and new paid services are outside this grant. Retain migration files and the deployment run-sheet; protect failure evidence before reset and settle only the run's owned resources during cleanup.

P2 is adopted in SPEC A2 and reflected in C03, C05–C06.

No migration or environment action has been performed while writing this specification.

### P3 — Evidence-backed test and measurement correction

A3 distinguishes changing the agreed behavior from repairing a demonstrably defective way of checking it. The lead can correct a test, fixture, harness, or measurement method when authoritative behavior and reproducible evidence establish the defect and a fresh verifier checks the repair and preserved coverage. Actual stricter project policy remains binding. Ambiguous or changed product expectations still require a product decision.

This cannot authorize skipped requested tests, lost discovery, hollow assertions, mocking away authorization, or an easier outcome chosen after a failed repair. Performance acceptance is set before repair; test-campaign acceptance retains original failure identities and complete final-suite evidence. P3 is exercised by N08, P04–P06, and T04–T08.

### P4 — Scoped learning and concurrent goals

Run state, project knowledge, and user-wide practices have distinct homes. Existing canonical memory/policy is reused across eligible providers; retrieval is scoped and source-aware. The lead consolidates related incidents and counterevidence, corrects proved factual errors and explicit user preferences without delay, and reviews substantive generalized process changes before publication. A later anecdote does not automatically reverse a validated rule. Insufficient evidence and no durable lesson are valid close-out outcomes.

Use one lead context per goal with shared host admission. The default is two executing goals, each with up to two top-level runtimes, bounded to four across orchestration. The source's existing two-runtime check is per Task and needs a shared admission layer for this behavior. Fair scheduling and supported checkpoint/yield prevent a blocked or long-running goal from indefinitely consuming all useful capacity; actual process ownership and narrower resource/account limits remain binding.

P4 is adopted in A4. Its knowledge, concurrency, and Command acceptance are requirements to build and demonstrate, not current runtime capabilities or authorization to alter Command during this spec task.

## Scope and engineering choices to keep separate

- Software briefs, new projects, and problem investigation are now in scope alongside finished specs. The lead resolves technical questions and handles delivery; it cannot invent unresolved business requirements or claim execution while the local machine is off. General non-software business operations remain outside this feature.
- A4 adds bounded concurrency across task leads. The per-goal two-runtime default and shared limits can constrain throughput; wider execution requires supported explicit policy and appropriate resources. More agents alone do not establish better outcomes.
- “Best agent” means an appropriate permitted profile for this assignment, improved by evidence. Memory and process learning are in scope; a universally optimal model, model self-training, and a separate learned-ranking service are not promised.
- Current identity rules and adapter restrictions still apply. Supported provider documentation or another product's adapter is not proof that DevManager's integration can perform unattended input/result/question/recovery handling. Step 4 must choose a compliant path and name its acceptance proof; it must not promise capability from a CLI launch alone.
- A5 adds reusable procedures and current-run event handling, not scheduled maintenance campaigns, cloud workers, or a new browser recorder. Existing browser recipes and native Secret entry still need qualification with task leads; they cannot replace Command's required Chrome checks.
- Completion ends at the authorized delivery boundary. Verified and committed software with a remaining manual deployment step can be the intended result. A required test that could not run cannot be relabeled as successful to reach it.
