# DevManager orchestration — native product experience

Status: SPECIFIED FOR STEP 4 — A13 — 2026-09-10.

This is the normative UI chapter of [SPEC.md](SPEC.md), incorporated by reference into that agreement. It defines the DevManager features the implementation team must deliver. The [reference gallery](visuals/reference.html) and its [capture manifest](visuals/manifest.json) make the intended composition inspectable. These are proposed design targets with illustrative data, not screenshots of implemented orchestration or a claim of user approval. Product behavior is defined here and in the SPEC; the gallery does not create requirements from incidental example copy or values.

Robin’s clarification concerns how we build these new features **inside DevManager**. Completing a general design system, a screenshot checker, or backend orchestration infrastructure does not deliver this experience. The implementation must expose the agreed capabilities in the native app and prove their real user journeys and appearance. General project-design practices from A9 remain supporting guidance; this clarification does not require a new cross-project design-management product.

## One coherent place to work

Keep the existing native window, board, recursive task panes, conversation, composer, and contextual tools. A goal is represented by its existing Task and accountable lead. The primary surface is that lead’s conversation. The board is where users switch between goals and see attention/wait state. Details belong to the selected goal and stay within its pane/contextual tool area.

Existing manual Tasks and their controls remain available. Add **New goal** alongside the existing new-task action in the board’s New menu; preserve the existing manual-task shortcut/entry. New goal opens a draft in the normal task pane, using the selected project as the starting context. A manual provider conversation is not silently converted into an autonomous goal. An explicit request to manage an outcome in an existing Task can enter the same goal flow under the SPEC’s admission/authority rules.

The visual targets use the current native shell’s dark, restrained direction, semantic status accents, project edge markers, compact chrome, and shared controls. They extend the existing composition rather than redesigning the whole application. Resolve real tokens through [Native UI System](../../docs/native-ui-system.md). HTML/CSS in the gallery is a design representation; production remains GPUI, and existing theme/density/scale preferences remain supported.

### Layout and information hierarchy

- Keep the board at the left with readable goal titles, project context, a concise state/reason, and pending-action counts. Use existing resizing/collapse behavior. Group required user attention separately from ordinary work and scheduler waits; retain access to paused, stopped, and delivered goals.
- Keep the selected pane’s native title/status row and existing view controls. Conversation remains the default; Terminal, Files, Changes, Browser, and existing contextual tools stay reachable. Opening details does not create a second task screen or detach the conversation identity.
- Add one compact goal summary above the lead’s current account: the outcome, current stage, and the next relevant action or dependency. Do not repeat the whole plan as chat after every update. A short account of actual progress and what follows occupies the conversation; raw agent logs stay behind inspection.
- Provide **Plan**, **Agents**, **Checks**, and **Knowledge** as sections of one task-scoped **Goal details** surface. Open it from links in the goal summary or the pane’s details action. It occupies the existing contextual tool slot and replaces the previous tool in that slot; it does not add an always-open second sidebar. Close returns focus to its invoking control. File, diff, artifact, and browser links use existing viewers and preserve a return path.
- While a goal is executing, the visible control is **Pause** and the overflow menu exposes **Stop goal**. A manual Task’s Done action cannot mark an unfinished goal verified. Closing its pane is a view action and does not stop the host. Delivered goals show their outcome and can be inspected or followed up; new work starts a fresh current outcome while retaining the earlier verdict.

At a narrow pane/window, collapse the optional details area into a single task-scoped overlay and retain a clear Close/back action. Use the existing board rail and pane zoom when needed. Keep the composer, pending decision, pause/stop path, and evidence entry reachable. Never shrink all controls or silently hide essential actions merely to fit the desktop reference.

### Steering, replay and delivery detail — A11

The Atomic review strengthens these states within the existing composition. The eleven A10 captures remain the base visual targets; they do not demonstrate these transitions. Use REF-RUN, REF-PLAN, REF-AGENTS, REF-RECOVERY, REF-DONE and REF-NARROW with the expected state differences below. Prepare any needed expanded reference before its implementation slice and prove it in the native app. No Atomic graph editor, broker controls, TUI palette or web variant UI is added.

- After a correction, the conversation first shows **Direction saved** when the host has durably accepted it. When affected assignments still need it, show a concise **Applying direction** state with its real remaining scope; opening Agents reveals which assignments are pending, using current direction, or need reconciliation. Show **Applied to current plan** only when the affected plan/assignment boundary is reconciled. A worker unable to take live input has an explicit safe-boundary/replacement state; its old result cannot silently advance the changed goal. Preserve the draft and current detail/focus context throughout.
- Plan identifies resumed versus newly executed work and any **Reconciling prior action** wait. Expanded work details link to the admitted method/plan version, evidence and the actual cause. A missing receipt is not presented as proof that an external action failed or never ran. Ordinary progress stays concise; diagnostic identifiers remain behind inspection.
- Checks retains each required outcome and finding disposition even if reviewers disagree or label it minor. A review opinion is shown as a judgment alongside its evidence, not as a replacement for a missing test result. Source and evidence links use existing viewers.
- When review is complete but an authorized final action remains, show **Review passed · delivery pending** and the actual next action, failure or reconciliation state. An unconditional verified delivery waits for all obligations at the requested stopping boundary. The existing **ready to deploy** reference remains appropriate when production deployment is intentionally outside that boundary.

### Sources, outcomes and shared knowledge — A12

The [Hamster/Taskmaster review](../../docs/research/2026-09-10-hamster-taskmaster-review.md) adds inspectable relationships and truthful state within REF-PLAN, REF-AGENTS, REF-KNOWLEDGE, REF-SPEED/TESTS, REF-DONE and REF-NARROW. Keep the same shell, typography, spacing, shared controls and navigation. These descriptions specify additional target states; the A10 images do not yet depict or verify them. Prepare any expanded target before the affected implementation slice.

- In **Plan**, selecting a requirement/work item reveals **Why this work**, its source/decision link, current acceptance and dependencies, and linked implementation/checks. Show a source's title and relevant version/section; open it in the existing viewer and preserve the selected item and return focus. A changed or restored source exposes what changed and which work/checks need reconciliation. Missing source content stays **Source unavailable** with retained permitted provenance. Invalid technical dependencies show **Repairing plan** with the actual next step; do not ask the user to manipulate graph edges.
- In **Checks** and the delivery account, show the agreed target and comparable observed result where applicable, including measurement conditions and freshness. Distinguish **Work delivered**, **Outcome measured**, and **Outcome not yet verified**; provide the precise pending measurement or access reason. A ready-to-deploy delivery can state that production impact was outside scope. A required measurement still pending cannot share the unconditional verified-delivery treatment. Task percentages and confidence must not visually impersonate measured success.
- In **Knowledge**, link the sources and research conclusion used for a decision, with established/provisional/conflicting/unavailable state. Product facts remain at their existing project home; reusable practices remain at the owning procedure. A delivery-linked update shows affected sections, rationale and actual proposed/published/validated disposition, using the existing diff/viewer and scope controls. Repeated completion does not duplicate rows or proposals. No new Blueprint library, knowledge graph canvas or general document editor is needed.
- In **Agents**, assignment detail shows the current context/procedure source and freshness, required tool availability and any supported discovery/requalification in progress. A stale copy shows **Updating context** only while owned work is actually resolving it; otherwise show the precise blocked state. These details stay behind inspection. The normal goal entry never requires users to choose a tool preset or manage copies of worker prompts.

The native slice must exercise real links, receipt-driven transitions, denied/missing/stale sources, plan repair, pending outcome evidence, concurrent knowledge edits and successful reconciliation. Apply the same narrow-layout, keyboard/focus, loading/failure and reference-comparison requirements as the base states. Research steps collapse after completion and leave the answer and source links reachable in the existing conversation; the full plan is not echoed into chat.

### Access, coverage and safe evidence — A13

The [BridgeMind review](../../docs/research/2026-09-10-bridgemind-review.md) adds variants within REF-AGENTS, REF-DECISION, REF-RECOVERY, REF-TESTS, REF-KNOWLEDGE and REF-NARROW. The eleven A10 images remain composition targets and do not depict or prove these variants. Prepare any needed expanded target before the affected slice, using the same shared rows, controls, typography, status colors and viewers.

- **Agents** keeps the role/assignment separate from its actual provider/model. Access detail distinguishes the selected mode from reported/observed restrictions and unavailable information. A refused required tool shows **Access did not match** with the blocked action and an actual recovery or user-only need, never a successful-completion badge. **Access changed** identifies affected queued/preparing work after revocation. A settings preference change cannot visually impersonate a completed handoff of a live conversation.
- An actual **Needs you** decision identifies the service, non-secret account label, action, target and known spending consequence, including credit-consuming reads. Use readable product consequences on the card; connection versions and protocol details stay behind inspection. Stale questions are withdrawn/settled with a reason, and replies cannot apply to a replacement account. Already-authorized work proceeds without a new confirmation. Preserve the current draft and task scope throughout.
- **Checks** exposes covered/skipped scope and tool errors alongside the result. No relevant coverage or an incomplete required category shows **Not verified**, with the exact missing proof and recovery. A heuristic finding is visibly distinct from a verified defect. Open its source in the existing safe viewer with file/section location, relevant hidden characters revealed, credentials redacted and embedded code/HTML/protocol links inert. Do not auto-execute or load remote resources from a finding preview.
- **Knowledge** and derived research evidence retain their originating source/version and evidence/proposal status. Show conflicting/unavailable provenance without turning a copied summary into a policy grant or a reassuring trust score. Normal authoritative project guidance remains readable and applicable under the SPEC's precedence rules. Correction still reaches the canonical home.

The slice must demonstrate provider refusal, revocation during preparation, an already-dispatched action awaiting reconciliation, an incomplete check, safe payload inspection and an authorized action that requires no extra click. Apply real host receipts, loading/error/recovery states, keyboard/focus return and normal/narrow matched native captures. These additions do not introduce new top-level modes, a security dashboard, a connector catalogue or an agent-configuration wizard.

## State and action rules shared by every new surface

1. Treat projection loading/reconnect as its own visible condition. Preserve readable prior state as stale when permitted, disable mutations until canonical readiness, retry through the supported path, and keep the user’s draft. Never turn an unavailable projection into an empty goal list or a permanent disabled composer.
2. Display host-backed facts with their correct scope. Agent replied, code built, check passed, goal verified, process stopped, and software deployed have different meanings. Unknown progress, usage, availability, or verification remains unknown. A timer is not evidence of an automatic retry or provider reset.
3. Every enabled control has a named real action, owned receipt, pending state, failure recovery, and keyboard/focus behavior. A disabled control explains its actual prerequisite. Do not ship dead tabs, decorative progress, placeholder panels, hardcoded successful counts, or buttons that only change local presentation.
4. Scope Goal details, browser handoff, source links, decisions, and controls to the current task/host generation. Changing goals cancels obsolete local requests and ignores stale outcomes while preserving unrelated projections. Query only the active bounded detail surface, following existing host transport limits.
5. Keep the current primary action available through supported window/pane sizes and appearances. Long task titles and findings retain access to full text. Status uses text/icon as well as color. Verify focus traversal, input, scrolling, dialog dismissal/return, disabled/loading/error states, and applicable accessibility/performance contracts against the rendered native app.
6. Fit new elements into the existing component vocabulary. Goal summary, milestone row, assignment row, evidence/finding row, scoped knowledge entry and decision card are shared patterns within this feature, with common spacing, typography and state handling. Extend their owning primitives once and reuse them across these targets.

## How step 4 must slice and prove the work

These are **coverage obligations**, not a generated phase plan. Step 4 settles the exact interfaces and phase ordering from the current code. A phase’s description must name its feature-to-surface rows, reference targets, actual host facts/actions, and user-journey checks.

For each user-visible capability, plan a vertical slice containing the backend behavior, real native wiring, representative states, and corresponding user/visual acceptance. A prerequisite infrastructure slice may exist where necessary, but it must identify its dependent user-facing slice and cannot count as delivery of that capability. There is no optional final UI/polish phase that completes the omitted product.

Each delivered slice has three separate evidence results in its normal tracking/audit records:

| Proof | Required evidence |
| --- | --- |
| Functional | Real host/action/state behavior and appropriate code/integration checks against current inputs |
| User journey | The named native entry, actions, state transitions, recovery and observable result, including real provider/browser interaction where required |
| Appearance | A current full canonical native capture paired with the applicable reference at comparable geometry/state; independent adjudication of material differences and legitimate allowances |

The implementation team must capture and inspect the actual native shell. HTML targets, old PNGs, synthetic quality surfaces, source assertions, and passing Rust tests cannot establish the appearance or live journey result. Preserve root AGENTS.md requirements for isolated builds, full-shell geometry, actual input acceptance, native process ownership, and host truth. Do not weaken the existing synthetic quality gates.

Before the release is called complete, reconcile the entire feature-to-surface table against what ships, run the native start-to-delivery journey including interruption and a real decision, and inspect all targets plus the required affected state matrix. Exercise A11’s accepted/pending/applied steering, contradictory review evidence, uncertain prior effect, and review-passed/delivery-pending states through their actual receipt transitions. Exercise A12’s source/decision/plan/evidence navigation, source edit/restore, stale context and permitted tool discovery, outcome measurement boundaries, and delivery-linked knowledge reconciliation against actual host state. Exercise A13’s selected/effective access mismatch, account revocation while an effect is preparing, current decision scope, incomplete coverage and safe transformed-source inspection; an already-authorized action needs no extra approval. Verify existing manual tasks and native contextual tools still work. Missing, placeholder, unreachable, unwired, stale, or unverified required surfaces are gaps to close, even when their backend exists.

## Authority and change control

The UI choices here are recorded technical/product-composition decisions within Robin’s stated native, conversation-first direction, available for correction.
