## Working Summary

### Purpose

Let Robin give one lead a software outcome and rules, then have that lead establish the necessary facts, plan the work, choose appropriate agents, integrate their changes, and obtain independent verification of the result. The input can be a finished spec directory, a project brief, a bug report, “this page is too slow,” or “fix these 300 red tests.” Writing a spec is not an entry requirement. Remove the need to paste successive prompts, choose each worker, transfer findings, restart forgotten work, or remind an agent to test its claims.

DevManager retains its native interface and durable local host. Standard coding harnesses perform reasoning, coding, tool use, context management, and supported native delegation. DevManager supplies the bounded coordination, workspace/process ownership, recovery, and evidence needed to complete this workflow.

Build the persistent lead experience into DevManager itself: one place to hand over outcomes, durable project/user knowledge, prepared tools and work environments, coordinated task leads and specialists, visible results, and validated improvement over time. Grok Bot informs those product patterns. Reuse supported harnesses, tools, libraries, and existing DevManager primitives to deliver them within this product. The user should be able to complete the accepted workflow through DevManager without opening a separate orchestration product or manually relaying work to it.

Apply the user's design values throughout: the fewest parts that deliver the workflow, explicit validated states and evidence, and the least routine effort for the user. Reuse capabilities that pass the actual acceptance contract. Additional agents, settings, process, and infrastructure must earn their cost by solving a demonstrated need.

### Who uses it

- A developer handing over a finished spec, a desired software outcome, or an observed problem and expecting the lead to steer the remaining work.
- The same developer checking progress, answering an actual product decision, inspecting evidence, pausing work, or resuming after interruption.
- Lead, implementation, review, audit, and E2E agent sessions operating under the project's existing rules.

### What success looks like

The user describes the work in the existing Task conversation. The lead determines what the request requires without a mode-selection wizard:

The product is successful when this complete process requires less human coordination than the same workflow run directly with standard agents or an existing coordinator. Agent count and a successful worker launch are not completion measures.

The user can keep several goals moving, in Command and other projects, without choosing which lead instance to create or manually transferring memory. Later work should benefit from validated earlier knowledge, fewer repeated mistakes, and simpler maintained guidance. A project can span several such units, and a remediation campaign uses bounded batches of related causes. A boundary updates progress and runs appropriate focused checks. Risky changes or project policy may require smaller landings. The lead must not invent a commit-to-`master` rule from the example prompt: follow the actual target repository's branch and landing policy.

Small edits take the direct path. Delegate when a bounded independent assignment saves work; do not require a worker, brief document, or review ceremony for every tiny edit. Keep design, ambiguous logic, and sensitive decisions with an eligible capable agent under project policy.

TRACKING distinguishes built work from verified work, using the project's established `[b]` and `[x]` convention when present. Record actual check results when upgrading verification. Capture required baseline failure identities before edits. Complete required tests and build checks before declaring the feature built and ready for independent acceptance.

Across separate repositories, record every required commit. A successful commit in `/api` followed by a failure in `/web` is partial landing, not atomic success. Preserve what happened and reconcile it before completion.

### Independent audit, testing, and fixes

A fresh verifier is a new conversation assembled from authoritative artifacts, policy, code, and prior findings needed for stable IDs. Do not include the builder's conversation history or private reasoning. A different model with the builder's full chat is not a fresh audit. Same-provider verification is allowed when the context and role are independent.

The landing review and full-feature audit are distinct responsibilities. If project policy requires Codex pre-commit review with ADOPT/REJECT adjudication, arrange it; that does not silently replace the later feature audit. Run shared global checks economically within each required verification stage, not once for every phase. Reuse evidence only when its inputs, independence, scope, and environment permit it.

The verifier checks the original goal agreement against both the implementation plan and actual behavior. For a spec run, this includes SPEC-to-build-doc and SPEC-to-code coverage. Trace outcomes to code and real observations, execute acceptance checks, and identify hollow tests or weakened assertions. An evidenced diagnosis alone does not satisfy a repair request. The verifier may judge a finding factually wrong from evidence; it may not quietly decide that a different product is better. Preserve MISSING, BROKEN, DIVERGED, EXTRA, SHORTCUT, VALUES, and INVARIANT classifications and blocking/should-fix/minor severity where the workflow uses them.

For any adopted reusable check or scanner, qualification covers relevant positive, benign, unsupported-scope and tool-error fixtures against the actual version. A run records what inputs/categories were applicable, what was actually covered or skipped, and any execution/parse/dependency failures alongside its completion receipt. Exit zero or no findings alone does not satisfy a required check when it examined no relevant files, used an invalid pattern, lost an error, or skipped required coverage. Mark the uncovered obligation NOT VERIFIED and repair the checking method or use a qualified equivalent within existing authority; keep prior observations and obtain fresh verification. A genuinely inapplicable category may be recorded with its evidenced reason. Pattern findings need source/context and consequence analysis rather than automatic severity or scope expansion. Reuse current qualification and keep checks proportional to the change; this does not require a new scanner or exhaustive security audit for every goal.

Classify finding scope separately from severity and confidence. Any unfulfilled requirement of the current agreement remains required even if a reviewer labels it minor or uncertain. Consolidate related reports by evidenced cause while retaining their original IDs, distinct affected requirements, sources, and dispositions; a matching title/path alone is not proof of one cause. A low-confidence finding may receive bounded fresh diagnosis, but numeric scoring or a reviewer majority cannot remove a required outcome. Close or dispute the finding through observed evidence and independent adjudication; keep genuinely optional improvements outside required repair scope.

E2E uses the real product. Capture every relevant service's logs, establish startup/idle noise, and correlate new log intervals with actions. Inspect browser console/network, empty/loading/error/partial-failure states, required personas, non-visual surfaces, and stated performance budgets. Pin actual routes and visible control labels back into TEST-PLAN. Preserve observed failures even if root-cause diagnosis is incomplete; assign investigation rather than dropping the finding. Distinguish observed timing association from a proven cause.

Fix blocking and should-fix findings, then only small, low-risk minor items allowed by the workflow. Do not weaken, skip, delete, or mock away acceptance checks to obtain green. A demonstrably defective test, fixture, or measurement may be repaired under the evidence and fresh-verification requirements in “Repair a failing-test campaign” below; this is not permission to change expected product behavior or hide a defect. Dispute a factually wrong finding with evidence and obtain independent adjudication. A materially changed acceptance outcome or agreed behavior needs the user's decision.

Keep finding IDs stable across reruns, including phase/cross-phase findings, rework, and E2E findings. Fix sessions add fix notes; fresh verifiers mark closure. Repeated unsuccessful repairs trigger the lead-owned recovery policy below rather than an automatic question to Robin after two rounds. Preserve failed approaches, actual outcomes, and the original finding through worker changes and restarts.

### Bounded recovery from difficult findings

The default is two ordinary repair attempts, followed by fresh diagnosis if the finding remains open. The diagnosing session must be independent of the failed repairs and must read the requirement, actual code, prior attempts, and their evidence. It identifies why the previous approaches failed and gives the lead a concrete alternative, an evidence-backed dispute, or a specific product/authority blocker.

The lead may then authorize up to two further materially different repair attempts, each followed by independent verification: four completed repair attempts per unresolved finding by default. A stricter explicit user budget can stop admission sooner; an explicitly selected project recovery policy can set a different finite limit. Do not repeat a rejected approach without new evidence, reset the counter by renaming the finding or changing providers, or weaken a check to obtain closure.

A repair attempt is a code repair submitted for verification with a completed relevant acceptance result. An unavailable test environment or crashed check is an incomplete verification attempt, not evidence that the code repair failed. Handle that condition through bounded environment/process recovery and resume verification without duplicating the writer. Counters and evidence survive restart; an in-flight productive command is not terminated merely because the next-attempt limit has been reached.

If recovery is exhausted while the finding is still unresolved, preserve the exact state and continue independent work. The lead presents one specific blocker with the failed approaches, independent diagnosis, last verified progress, and the smallest input or authority change that could help. It must not claim completion, wait under an unexplained Running label, or start another hidden repair loop. Independently verified progress means demonstrated behavior/check improvement; narration, more messages, or relabeling a task is not progress.

Judge scope against the user's goal. Pre-existing failures expressly included in “fix this suite” are in scope; they cannot be sent to the backlog simply because this run did not introduce them. Genuinely unrelated problems go to the existing shared tracker after duplicate/recurrence checks and do not automatically enter implementation scope. Auditors supply evidence and proposals to the lead-owned consolidation procedure in “Memory and sharpening the axe”; they do not silently rewrite the policy they are auditing.

## Problem-led investigation and repair

### Resolve a slow page or interaction

Resolve the reported page, persona, operation, and relevant data from the task and actual application. Reproduce the symptom before claiming its cause. If the problem appears only under unavailable production conditions, use authorized observations and a representative isolated reproduction where possible; state the gap if neither demonstrates it. Do not equate a local clean profile or a faster unrelated endpoint with repairing the reported experience.

Record the baseline measurement recipe: page/action, visible completion condition, application revision/build mode, device/browser, network conditions, data volume, service/fixture identity, and cache state. Distinguish initial navigation, warm interactions, API latency, rendering, and background work. Inspect the relevant browser timeline/network, server logs/traces, and query behavior to locate the bottleneck. A plausible N+1 explanation without supporting observation is a hypothesis. The lead chooses tools and experiments itself and records which evidence supports or rejects the repair approach.

Use existing project/user performance targets first. Otherwise apply the established 500 ms warm API/data-visible default when those are the reported operations. That number is not a universal total-page-load, cold-build, or bulk-operation budget. For other operations, choose and record a justified numeric target before repair, including the visible outcome and representative workload. If satisfying the outcome would require changing product behavior or material spending, raise that concrete decision; do not make the user choose profiling or implementation techniques.

The default comparison uses three warm-up interactions followed by at least twenty measured repetitions of the same operation on both starting and repaired versions, recording individual measurements, median, and p95 using nearest rank. Record the statistic as well as the numeric target before repair; without a project rule, apply the warm target to p95. Repeat the final measurement set during independent verification and require it to meet the same target. For a specifically cold-start problem, record at least three separate starts and their individual timings; do not advertise a reliable tail percentile from three samples. Established project measurement rules can replace these defaults. Record a justified alternative for a destructive or unusually costly operation before measuring. If noise prevents a meaningful comparison, improve the experiment or report the uncertainty instead of selecting the fastest run.

Keep conditions comparable: do not achieve the target by shrinking data, warming only the repaired version, dropping returned fields, weakening authorization, hiding an error, or showing a spinner sooner while useful content remains slow. Verify the original user interaction, relevant empty/error states, and affected correctness/regression checks after the change. Check moved costs such as slower writes or newly expensive background work when the repair introduces them. Acceptance needs the recorded target met on the final integrated application, repeatable evidence of the intended improvement, and independent verification; a microbenchmark alone is insufficient for a user-visible complaint.

### Repair a failing-test campaign

Treat “300 red tests” as a description to verify, not a fixed expected count or a request for 300 agents. Resolve the intended suite from the active project, supplied report, and commands. When the user says “fix all red tests” without a narrower selection, the goal covers the project's required suites, not merely the subset that starts green. Record discovered test identities, parameterized case identities when exposed, failing test/file identities, execution errors, command filters, and actual completed baseline results. Keep a stable mapping to the original reported failures when names change for a justified reason.

A process that OOMs, crashes, times out, fails setup, or produces no completion summary has not established a complete red-test inventory. Diagnose and repair authorized environment/setup problems, preserve the partial evidence, and obtain a complete run. Respect the target project's resource/isolation rules; in DevManager that includes one quiet, serial full Rust suite and owned compiler processes. Do not compare failure counts alone or promise that an incomplete baseline proves there are exactly 300 failures.

Group failures by evidenced root cause and dependencies: application behavior, common fixture/setup, outdated or incorrect test, environment, and timing/concurrency/flakiness. Record suspected groupings as hypotheses until checked. One shared defect may account for hundreds of failing cases. Assign bounded root-cause repairs, serialize overlapping source/shared-state work, and parallelize only genuinely independent assignments within supported capacity. Verify affected cases after a batch and run the required integration/full-suite gates on the combined result. Progress shows original failures independently resolved, still failing, unverified, and newly exposed, plus root causes repaired; “agents finished” and a falling count are insufficient.

Pre-existing failures within the requested suite are the goal, including environmental failures that can be repaired within authority. A “standing red baseline” is not a completion waiver for them. Newly exposed failures in that same suite are included in making it healthy. New failures introduced outside it must also be fixed; genuinely unrelated pre-existing failures outside the agreed scope retain their documented disposition. Do not silently expand a named subset into an unrelated feature rewrite or shrink “all tests” into a convenient subset.

Repair application defects in application code. A test/fixture/harness may itself be wrong: the lead may correct it when authoritative behavior, current contracts, or a reproducible defect in the test proves why, and a fresh verifier independently checks that reasoning and the replacement coverage. For a regression assertion, demonstrate sensitivity to the defect it is meant to catch, using a failing-before/fixed-after run or a focused equivalent check when feasible. Do not require a human decision for a proved fixture path or test harness defect. If expected product behavior is ambiguous or would change, retain the failure and ask for that product decision.

Never obtain green by disabling test discovery, skipping/quarantining requested cases, removing meaningful assertions, mocking away the boundary being tested, blanket timeout inflation, automatic snapshot acceptance of broken output, or weakening authorization. A legitimate timeout, snapshot, or assertion correction needs a documented cause and independent evidence that the intended behavior and coverage remain intact; stricter actual project policies still apply. Changed test identities and discovery manifests must be reconciled so deletion or renaming cannot hide unresolved failures.

For intermittent failures, preserve the seed/order/concurrency and known reproducer when available. Fix the underlying condition and repeat the affected cases under the conditions that exposed it. With no project rule, use at least twenty repetitions of the recorded reproducer after the repair, plus the full requested suite; when the observed failure frequency makes that insufficient, choose and record a larger evidence-backed sample before claiming closure. A single lucky green run cannot close a known flaky failure, and a finite clean sample is not proof that flakiness is impossible.

The bounded repair policy applies to each persistent unresolved cause/finding, not four repairs for the entire campaign and not a fresh allowance for each of 300 symptoms of the same known cause. Preserve root-cause links and consumed attempts through merges/splits of findings so relabeling cannot evade the bound. Successful independently verified batches may continue across the whole campaign within the run's budget. If a particular cause exhausts recovery, finish independent causes and retain a precise blocker for the unmet suite outcome.

Completion requires a completed full run of the requested suite on the final integrated inputs, every requested original failure reconciled to verified resolution, no hidden missing/skipped cases, required regression/build gates, and current independent closure. If a required service cannot be accessed or a test remains unresolved, report partial progress rather than “fixed 300 tests.” The user may explicitly change the scope; record that as a changed agreement, never as evidence that the excluded test passed.

## Roles, routing, and questions

### Choose the worker from the task and permitted capabilities

The lead chooses among profiles the user has already permitted. A profile means the harness, model/settings, tools, environment, and role permissions together. Use actual executable/capability evidence and project preferences. Do not hardcode a global ranking of model names, assume consumer subscription quota, or quietly switch to a paid API account.

For Robin's supplied workflow, the initial preferences are Claude for lead judgment and difficult work, Cursor for suitable mechanical work, and Codex where the landing policy requires review. These are project preferences, not mandatory dependencies for every user's project. A configured eligible Codex lead must also be able to run the workflow. Optional Cursor support must not block a project that does not require it.

When no project role preference exists, keep the current eligible lead and select eligible workers under the user's existing provider settings. Explain a material selection or permitted fallback briefly in the run record. If a required role has no eligible permitted profile, name the missing capability and continue independent work. Do not make the user choose an agent for every stage.

Match assignments to concrete needs: repository/stack knowledge, read or write authority, required tools, context size, review independence, resource availability, and any applicable quality/cost preference. When comparable verified outcomes from earlier assignments are available, use them to avoid repeating a demonstrated mismatch. Retain the relevant evidence and selection reason in existing run records; do not invent a success score when no comparable history exists or create a separate learned-routing service for this release.

Required capabilities are eligibility constraints, not ranking preferences. Every fallback must retain the assignment's required tools, ability to interpret its inputs, effective authority, verification independence, and supported identity contract. Do not silently remove screenshots, tool access, required evidence, or acceptance to accommodate a weaker profile. Rank only eligible permitted candidates. If none qualifies, expose the exact unmet capability and continue independent work.

A visual implementation/review assignment must receive its current reference images and be able to inspect the required rendered evidence through its qualified tools. A textual description, source-only review, or an image path the worker cannot open does not establish visual review. The lead can assign the design/review responsibility to an eligible existing role; this does not require another permanent agent hierarchy.

Preserve a working assignment's qualified profile and conversation while they remain suitable. Do not rotate its provider/account on each message for load balancing or an unverified cheaper-model preference. Record a material route change and its reason through the supported requalification/replacement path. A combo/display alias is neither proof of the actual provider/model nor a conversation ID. Record reported configuration and unavailable detail honestly; a native harness's supported model change cannot justify fabricating exact-resume identity. Assess routing quality by comparable verified assignment outcomes and human effort, not request success, first-token speed, or model agreement alone.

Choose the work surface as deliberately as the agent. Prefer a current local source, existing project command, or permitted structured tool when it provides the required operation/evidence with less cost and fragility; use browser/computer interaction where the actual behavior or project check requires it. Discover existing supported tools before asking the user to perform routine work. This is an evidence-based preference, not a mandatory ladder of failed calls. An API success cannot replace required user-visible verification, and DevManager's embedded browser cannot substitute for Command's prescribed Chrome measurement. A refusal of an effect is not a reason to attempt that same forbidden effect through a shell, another connector, or UI clicks; genuine capability failure may use an authorized equivalent.

If a worker lacks a required capability, produces an unusable result, or becomes unavailable, the lead must diagnose the condition and try an eligible permitted alternative when one exists. Reassignment carries a concise evidence-based handoff, preserves the work and finding IDs, and settles the exact previous writer before replacement. It does not authorize switching account/billing modes, violating a required review role, resetting fix-round limits, or representing a different provider conversation as an exact resume.

The lead may use native subagents where the provider and policy allow them. DevManager owns the cross-provider assignments it launches. Do not create a second loop that repeatedly sends “continue” while the provider is already executing its native continuation. Attribute native children only through supported correlated identities; show unavailable detail as unavailable.

Keep the tool/context surface proportional to the assignment. Where a qualified harness supports selective tool exposure, provide the exact registered tools needed for its role and a supported way to discover/request an additional permitted capability; otherwise account for its actual fixed catalogue or select another qualified profile. Test the real capability intersection and required tool discovery, not just tool names, advertised compatibility, or estimated schema-token savings. Discovery, registration, reachability and effect authority are separate checks. A reduced catalogue must not omit mandatory guidance or required verification tools, and expanding it never expands permissions. Report unsupported/missing capabilities precisely rather than claiming the task is impossible because a tool was hidden or accepting an arbitrary name as registered.

### A provider must prove the capabilities its role needs

An executable existing on disk or accepting a prompt is not sufficient qualification for unattended work. Before a profile is advertised for a role, the installed DevManager/provider combination must demonstrate the applicable capabilities below. A role may require a subset, but the complete workflow needs all of them through qualified profiles and tools.

| Capability | Required observable result |
| --- | --- |
| Correlated assignment and input | Launch/attach and deliver instructions to the intended current session/attempt, with an identifiable admission or failure. |
| Lead coordination | The lead can request work, receive correlated results, consult run state, and continue without a person copying messages. |
| Turn and question state | Distinguish an active turn, a returned result, a request needing an answer, an exit, and an unavailable state. Quiet terminal output is not turn completion. |
| Decisions within authority | Route a provider question to the lead/host and answer an already-authorized action through its supported interface; otherwise keep the exact decision pending. An answer must not expand the assignment's authority. |
| Evidence and independent verification | Bind results/check receipts to the assignment and source context; start a fresh verifier without the builder's chat history. |
| Stop and recovery | Settle the owned process tree and recover using supported exact identity or a visibly distinct, authorized replacement assignment. |
| Scoped memory and concurrent goals | Deliver/retrieve current applicable canonical guidance in separate goal contexts, correlate results/questions to their own goal, and prove safe checkpoint/yield/resume needed by shared admission. |

The supported control path is a step-4 engineering decision constrained by current identity and authority rules. If the existing adapter cannot prove a required capability, implement a compliant path or report the exact unresolved prerequisite before calling the plan buildable. Terminal scraping, manual prompt copying, fixture-only success, and uncorrelated JSON cannot substitute for live qualification. This requirement does not waive the current adapter's restrictions.

Qualification is bound to the executable/integration version, configured tool surface, account mode, and role requirements actually checked. A changed executable, revoked tool, expired login, or incompatible provider update invalidates affected capabilities before new work relies on them. Recheck narrowly, preserve unaffected work, and choose an already-permitted fallback where possible. Record reported model/settings and unknown version details honestly; do not claim visibility into opaque provider changes or repeat the entire qualification suite for every ordinary assignment.

Qualify effective behavior through the actual control path, including provider refusals and shell/tool-mediated effects. A selected access setting, a role named read-only, or removal of named editing tools is not enforcement proof. Record the selected profile and reported/observed effective restrictions, with opaque details marked unknown. A provider that rejects the requested mode or refuses a required action has not completed that action even if its turn exits successfully. Reconcile the affected capability/attempt and use an eligible permitted recovery or expose its precise blocker; never broaden access to make a label true. Changing a default role/model preference affects future assignments, while changes to current authority take effect through steering/revocation. Neither change silently retargets a live provider conversation.

### Decision authority

| The lead decides and records | The user decides when unresolved by existing authority |
| --- | --- |
| Reproduction, profiling, test-failure classification, measurable engineering acceptance, and project decomposition within the requested outcome | Missing business behavior, a different requested outcome, or a material scope reduction |
| Stage transitions, phase-document continuation, worker selection within allowed profiles | A material change to specified product behavior or scope |
| Technical implementation details consistent with agreed behavior and invariants | An invariant or exact approved external contract must change |
| Commands/conventions established by repository evidence; routine technical repairs | An acceptance requirement must be changed rather than implemented |
| In-scope code fixes, proven test/setup defects, and evidence-backed factual dispute resolution through fresh verification | New spending/account authority, credentials only the user can supply, or an unauthorized external action |
| Owned disposable-test setup and migrations, eligible fallback, rescheduling, and fresh diagnosis after repeated failed repairs | The explicit recovery/budget limit is exhausted, or a required action remains outside current authority |
| Scoped memory maintenance, evidence-backed process consolidation, task-lead creation, and fair scheduling within configured limits | A proposed learned rule would relax a protected requirement, expand authority, or reverse an explicit user/product decision |

Worker questions go to the lead first. Reuse applicable settled decisions and facts, with their scope and source. The lead asks the user only after attempting to answer within authority. Present one concise material question with a recommendation and consequences when there is a defensible recommendation. Keep it pending until answered; elapsed time, silence, or a worker's assertion is not approval.

An answer applies to the decision and scope it covers and persists across sessions. Do not ask again merely because another worker takes over. After the answer is recorded and affected artifacts reconciled, resume automatically. A changed scope or context may require a new decision; do not apply an unrelated old answer.

Correlate each pending question and answer to the current run, decision version, requesting attempt, and affected scope. A response to a withdrawn question or superseded plan cannot authorize its replacement. Simultaneous client answers settle one current decision consistently; show the settled answer rather than silently choosing whichever text a worker saw last. The lead deduplicates equivalent worker questions and supplies already-settled answers. If user-only input is required, retain the decision after reconnect, stop unrelated repeated reminders, and show exactly which work is waiting.

For a connected capability, distinguish registration, authenticated account, assignment eligibility and permission for the particular effect. Bind any needed decision and subsequent dispatch to the actual service, non-secret account reference, action, target, applicable connection/authority version and known cost/budget consequence, including credit-consuming reads. Unknown cost is not assumed zero or unlimited. Existing user authority is reused; do not add a confirmation for an already-authorized action. A failed attempt to verify a replacement connection leaves the current valid connection intact unless it was explicitly disconnected. Disconnection, account replacement or narrower permission invalidates affected prepared/queued operations and old answers before they can dispatch, including work still awaiting credential preparation. Reconcile any already-dispatched effect honestly under the existing uncertainty/replay contract, without claiming revocation undid it or retrying against a different account. Resume after current permitted access is actually re-established.

## Memory and sharpening the axe

### Three scopes, with existing authoritative homes

| Scope | What survives | What it must not become |
| --- | --- | --- |
| Goal/run | The agreement, current work, decisions, attempts, observations, findings, evidence, and recovery point | A second backlog or a universal instruction based on one incident |
| Project | Verified architecture/conventions, domain decisions and rationale, relevant root causes, valid negative findings, local procedures, and references to current policy/tracker evidence | A copied transcript, stale deployment-status ledger, or instruction for unrelated projects |
| User-wide (universal) | The user's applicable working preferences and validated general practices that are useful across projects | A copy of project-specific facts, credentials, customer data, or permissions for every environment |

Memory is shared across a user's task leads within its scope and survives context replacement, provider changes, and host restart. Reuse existing canonical homes before creating new ones. For Command, that includes its `.memory/` index, actual playbooks, and TODO/DONE conventions. Existing user-level preferences can remain in their established files. The host records ownership, source references, versions, and retrieval/publication facts; it does not create a competing editable copy of those rules. Provider-private auto-memory is an input to reconcile, not the only durable record or an automatically trusted authority.

An entry or its referenced source identifies what kind of knowledge it is, where it applies, its evidence/decision provenance, relevant source/environment versions, and whether it is established, provisional, contradicted, or superseded. Preserve enough of the prior rationale and counterevidence to understand a later reversal. Current task status stays in the tracker/host, linked from memory when useful. Do not import dated “deployed,” “all green,” database addresses, or temporary provider failures as current facts without checking them.

Maintain a small index with references to the owning sections. If guidance moves, update its references and retire duplicated bodies while retaining version history. Existing file names, import chains, and provider configuration are not rewritten merely to adopt DevManager. Any retrieval index or cache must be rebuildable from the canonical sources. A vector database, memory graph service, and model training are not required for this release.

### Retrieve, verify, and apply

At admission and recovery, load the user preferences that apply, mandatory project/host guidance, and the goal's working state. Retrieve additional relevant knowledge before diagnosing, choosing an implementation approach, or repeating an experiment. Consult prior resolved/failed approaches and their conditions as well as successful recipes. A DISPROVEN hypothesis for the same conditions should not be rediscovered as new; changed source, environment, or contrary evidence can justify reopening it with a recorded reason.

Use project/goal identity, knowledge type, source validity, and relevance to select a bounded context. Do not load every project memory into every worker or let an arbitrary top-k search omit a binding rule. Mandatory instructions must be delivered and their source/version accounted for before dependent mutation. If the integration cannot load them within its supported context/tool path, expose that specific limitation instead of claiming the policy loaded. The lead must be able to show which sources informed a decision and retrieve the original when needed.

For host-produced context views and retrieval tools, bind an omitted-detail reference to its owning scope, canonical source and immutable version, and the reader’s current access. A content hash identifies content; the current authorization check permits access. Retain the source version while active work or a recovery checkpoint depends on it, subject to existing redaction and retention policy. Cache eviction must recover that same version from canonical storage or expose missing evidence and re-establish affected checks. Today’s changed file cannot silently replace the original. Label partial views and make omitted material retrievable in bounded portions; release material when it is no longer required under the actual retention policy.

Qualify memory access through each supported provider role: an eligible Claude or Codex lead must receive the same applicable canonical guidance and be able to retrieve relevant project knowledge through its supported integration. Do not assume a Claude auto-memory setting makes a Codex worker aware of the same files. Fresh verifiers get the agreement, required guidance, and relevant evidence without the builder's chat or speculative conclusions being presented as facts.

Memory never grants new authority. Distinguish a remembered user directive with its actual scope from a learned suggestion or external/worker text. Revalidate volatile facts against current source/environment and handle contradictions by provenance, applicability, and current instructions, not recency or frequency alone. Uncertain knowledge can guide investigation but cannot certify a pass, lift a restriction, or overwrite a product decision. No credentials or sensitive project content are automatically promoted into universal memory; promotion carries only an applicable generalized practice and permitted provenance.

Default new knowledge to its narrowest useful scope. Promotion to universal practice must explain what generalizes and check at least one other representative project context; learning the same project-specific convention twice does not make it universal. An explicit user-wide preference needs no artificial recurrence requirement. Retain applicability conditions so a portable principle does not override a justified local rule.

Give each qualified harness a view of the same canonical goal, applicable procedure and assignment context through its supported files or tools. Any generated instruction adapter, context index, or local projection records its source scope/version and is replaceable from that authority. Keep one maintained behavioral body; generate unavoidable client-specific copies and check for drift, including local edits, missing referenced sections and conflicting copies. Preserve existing user-owned instruction files rather than overwriting them during setup or synchronization. Reconcile changed sources and requalify affected assignments before dependent mutations; stale/offline views remain labeled historical context, not an independently editable agreement or permission source. Readable cached context can support authorized investigation while freshness/authority requirements determine which further work may proceed. A new public CLI, hosted MCP service, or cross-client plugin distribution system is not required to supply these views.

### Consolidate evidence before changing the process

At a verified milestone or substantive task close-out, first merge unresolved work into the actual project tracker, checking completed history for recurrence. Then review observations, user corrections, failed approaches, independent audit findings, and successful outcomes that bear on the same problem. During interruption or unfinished work, preserve observations as provisional so recovery loses nothing; an ordinary returned model turn is not a trigger to rewrite the process.

Group by underlying cause and context. Several reports or hundreds of failing tests from one defect are one incident, not independent corroboration. Search the relevant rules, skills, prompts, configuration, memory, and prior revisions; include evidence that the existing approach worked and reasons alternatives were rejected. Decide whether the apparent conflict reflects stale facts, different contexts, a local defect, or a recurring process failure before proposing a replacement rule.

An explicit user correction applies within its scope immediately. A demonstrably wrong factual reference can be corrected from verified evidence without waiting for another failure. A single ordinary incident can become a scoped observation or local fix. A generalized change to working defaults normally requires at least two independent evidenced incidents or evaluations supporting the same cause, plus checks against representative successful cases; the number alone does not establish a sound rule. Strong deterministic evidence of an incorrect rule can justify a correction sooner, with its proof and scope recorded. Do not turn every anecdote into a ban or wait for preventable repeated damage to correct a proved falsehood.

Synthesize the smallest coherent remedy. Prefer fixing an executable check, tool, or configuration at the source of the recurring error when that repair is authorized and justified; otherwise rewrite the owning guidance section. Merge overlapping explanations, remove obsolete branches, retain necessary context-specific exceptions, and update all references. One maintained principle should replace overlapping incident notes. Do not append a “lessons learned” list to a frequently loaded file or create another mandatory ritual merely because a run was difficult.

When learning from a failed attempt followed by a correction, establish that the later outcome was verified and that the correction addresses the same cause. A generated marker block or heading-based merge is only a publication mechanism: reconcile the whole affected canonical guidance, including prior rationale and valid exceptions, before activation. Cache eviction without retrieval, a zero exit from an unhelpful search, and repeated summaries are observations with unknown task benefit until outcome evidence establishes otherwise.

The lead may maintain ordinary memory and improve rules/process within the user's existing authority. An auditor supplies evidence and proposals; it does not edit the policy it is currently judging. A substantive process change gets a fresh review of the synthesized diff, supporting cases, counterexamples, and intended effect before activation. Mechanical consolidation or a proved reference correction needs proportionate validation, not a full application audit. Changes that expand permissions, relax acceptance/invariants, alter the user's budget limits, or reverse an explicit product choice remain scoped user decisions. Learning cannot authorize its own exception.

Use verified delivery to reconcile the knowledge that the change actually affects. Follow the goal's source/decision/implementation links, check current code and canonical project guidance, and update a now-wrong factual section or prepare one coherent process-change candidate under the rules above. Keep factual maintenance distinct from generalizing a working method: a changed route can justify correcting its reference; one difficult repair cannot justify a universal ban. Repeated close-out/wakeup for the same goal and delivered version reuses its disposition instead of duplicating proposals or starting a new job. Preserve concurrent human edits, distinguish proposed/published/validated state, and make changed knowledge available to later leads only at its actual activation boundary. Do not maintain a second Blueprint library, rewrite unaffected guidance, or introduce schedules to perform the existing close-out obligation.

### Keep reusable methods separate from run history

## Concurrent goals and separate task leads

### One accountable lead per goal, one place to steer

Use a separate lead context and durable run for each goal. The existing Task conversation is its primary conversation; the cockpit also shows the user's goals across projects. Status, answers, corrections, priority changes, and cancellation target the selected or explicitly named goal; ambiguous targeting is resolved before acting. “Stop this task” does not stop other tasks. Do not kill productive compilers to enforce a wall-clock rotation. An idle or blocked lead can release its runtime only after a durable checkpoint and proven settlement of its owned activity; resume using supported identity/handoff rules. A profile that cannot yield safely keeps its real resource ownership visible. No parent may hold the only capacity needed by its own dependency.

Coordinate source, integration, ports, test databases, build targets, browser/session and interactive-input resources, exclusive verification lanes, artifact publication, and memory writes across goals as well as within one goal. Do not merge unrelated product scope into one goal merely to simplify scheduling. Keep provider-reported reset times distinct from locally chosen bounded recheck times; a shorter local backoff does not establish earlier quota availability. Unsupported scope or quota detail remains unknown. Derive current eligibility from these facts rather than synchronizing another editable health flag or storing temporary limits as universal memory.

Admit recovery under the shared limits, then reconsider each waiting goal fairly under its current authority. Use supported observations and the existing authentication owner; this requires neither a separate credential-refresh manager nor speculative paid requests to discover quota.

## Completion and delivery

Successful completion requires all of the following; the finished-spec workflow calls this verdict SHIPPABLE:

- The original goal agreement and amendments are covered by actual delivered behavior and verifiable checks; every required project milestone is included.
- Every required outcome, phase, and acceptance check is verified against final participating workspace versions; required build gates pass. A slow-page goal meets its recorded performance outcome; a test campaign meets its requested-suite closure rules.
- Blocking and should-fix findings are independently closed; remaining minor items and permitted out-of-scope pre-existing failures are explained. Requested pre-existing test failures are not exempt.
- A target project’s required UI outcomes and visual/interaction checks are verified when applicable. The release of this DevManager feature additionally satisfies UX-SPEC.md’s complete native feature-to-surface map, current reference comparisons, and live user journeys; UI delivery is not an optional final phase.
- Required audit and real outcome/E2E evidence are current. Inapplicable checks have reasons; unavailable required checks remain NOT VERIFIED and prevent an unconditional success verdict.
- Required review decisions and repository landings are recorded, without an unresolved partial landing.
- Owned assignments/effects are settled and the authorized delivery boundary is reached.
- The required close-out sweep and Axe report have a durable disposition. Knowledge changes claimed as applied are actually published/validated; a candidate awaiting evidence or authority is recorded honestly and does not become a reason for an endless learning loop.

Completion is evaluated by the host against the canonical required-outcome map, current independent dispositions, actual execution receipts, and settled effects. Reviewer stop flags, confidence scores, empty queues, and vote counts are judgments or signals, never substitutes for these facts. Contradictory, missing, malformed, or stale evidence prevents the relevant pass; the lead diagnoses and resolves the discrepancy rather than accepting the most optimistic report.

Classify completion obligations at planning into implementation/outcome evidence, independent review-process obligations, and final delivery effects, with explicit dependencies and the requested stopping boundary. A reviewer of the implementation need not certify its own future quorum or a later publication. The host evaluates the review-process obligation when its independent results exist, then admits any final action already authorized by the user and project policy. The whole goal completes only when all obligations due at that boundary have current evidence. A failed or uncertain final action remains incomplete and is reconciled before retry. Infer this sequencing from the agreed outcome; do not ask users to rewrite their request around a workflow flag or exempt requirements through text/keyword matching.

The lead conversation remains available for follow-up under the existing Task lifetime. An idle lead session is compatible with completion; a worker wrapper that can still perform queued writes is not settled work.

Completion is scoped. “Ready to deploy” does not mean deployed. The lead executes required migrations in its explicitly owned disposable test environment under the grant above and produces the migration files and production run-sheet. Production/shared-environment changes and publication still require their applicable authority. If the actual test environment cannot be provisioned within those boundaries, dependent checks stay NOT VERIFIED with the exact missing capability. Ordinary local implementation authority does not authorize publication or messages to others.

The final verdict refers to one coherent set of goal-agreement, source, generated-artifact, and environment versions. Before publishing it, reconcile active writers, outstanding effects, changed bases, and missing evidence so no accepted write can immediately invalidate a supposedly current verdict. Later authorized edits retain the historical verdict for its original inputs and visibly require fresh affected verification. A paused or stopped run retains useful partial work and its actual status; it is not silently converted to success.

Report the requested outcome and what was achieved, significant decisions, current measurements and verification results, exact repository revisions, remaining limitations/manual actions, and durable evidence. If incomplete, name the unmet outcome and specific unresolved condition with preserved progress. Never substitute “all agents finished,” “plan written,” or “most failures fixed” for acceptance of the whole requested goal.

The delivery report distinguishes **work delivered**, **outcome measured**, and **outcome not yet verified** according to the agreement. Report comparable observed values and conditions where required; do not infer causal business improvement from a successful code delivery. When later measurement is outside the authorized boundary, state that limitation alongside the verified delivery instead of declaring the unmeasured result achieved. When it is required, continue or preserve the precise unmet measurement condition under the existing time/access/budget rules.

## Full acceptance run and comparison

The release must demonstrate each of these distinct workloads through the actual lead/host integration. An existing spec-run success does not establish problem-solving or project-steering acceptance.

| Required workload | Starting input and observable completion |
| --- | --- |
| Finished-spec delivery | A representative finished spec with no `LOCKED` marker or build directory, several phases, and two participating repos. Complete generation, implementation, fresh audit, real E2E, an injected in-scope defect, repair, and independent closure. |
| Project from a brief | A software brief without a spec, containing several outcomes and dependencies across milestones. Include an authorized empty-workspace case. The lead prepares its agreement and setup, delivers the whole project, and verifies cross-milestone behavior. Exercise a genuine business decision separately and prove independent work continues. |
| Slow-page repair | Only a reported page/interaction and project context, with a reproducible bottleneck and representative data. The lead establishes the baseline and target, diagnoses, repairs, and independently repeats comparable measurements and functional checks. Retain all samples and rejected approaches. |

Complete diagnosis, batches, integration, discovery/identity reconciliation, required repeat checks, and a fully passing requested suite. Inject incomplete-run/setup and coverage-weakening cases into the corresponding refusal/recovery checks. |

Problem-only inputs must not gain a prewritten solution, root-cause hint, or hidden product spec from the test operator. Fixture authors may retain expected causes separately to evaluate the result. A single tiny repair or fabricated provider/test transcript cannot substitute for these workloads. Include an interruption during unfinished project/campaign work and prove continuation from its actual evidence. Classify genuine product input separately from avoidable orchestration handoffs.

Ground the finished-spec/maintenance workloads in authorized Command development work or faithful isolated copies of its actual participating repositories and policy. Include a vertical feature across relevant application surfaces, a maintenance/gate repair, and its applicable performance measurement contract. Exercise DevManager as another real project with its own Rust/native/provider boundaries. Deterministic fixtures supplement these cases for controlled failures; a toy API/web-only fixture cannot alone qualify the primary Command workload. Record missing environments/access as limitations, not fabricated acceptance. This specification does not itself start those runs or authorize production mutation.

Memory acceptance spans several tasks and a lead/provider replacement. Adopt existing canonical knowledge, retrieve a relevant negative finding, detect a stale fact, and prove that only applicable general preferences cross from Command to DevManager. Consolidate corroborated observations into one reviewed rule revision, test a valid counterexample, then exercise contrary evidence, a user correction, concurrent publication, and interruption. Reuse one consolidated procedure in a later task with changed inputs; detect a stale precondition and obtain fresh evidence without spawning a scheduled run. The resulting Axe report and later retrieval must correspond to actual published versions. A copied memory file or a self-reported “lesson learned” alone does not pass.

Concurrent-goal acceptance includes at least three admitted goals: two Command goals with a real overlap/dependency and a DevManager goal. Demonstrate two making progress at once under the default bounds, the third queued and later admitted fairly, scoped user input/stop, exclusive test-resource handling, shared account limits, memory-write reconciliation, integration invalidation, and restart recovery. A provider-specific inability to checkpoint or preserve ownership is a failed capability requirement, not an excuse to hide duplicate leads or claim concurrency from sequential transcripts.

Within those runs, verify tools and access from the actual worker environment, including a mismatched endpoint/persona and expired access recovered through a supported secure handoff. Exercise browser/profile contention and human takeover with stale queued input; qualified native replay primitives do not alone prove these task-lead interactions. Test direct-tool selection separately from the required real browser/performance surface. Retain evidence of deduplicated action needs and correct scoped resumption without secrets in the resulting records.

For DevManager itself, trace every UX-SPEC feature-to-surface row to its implemented native entry, real host facts/actions, required states, and current functional/user-journey/appearance evidence. Capture the new goal surfaces against the provided references at comparable geometry/state and independently review material differences. Inject a backend-passing but unwired UI, an unreachable or placeholder detail, a matching but unusable control, misleading/stale capture evidence, a self-created baseline, and a shared-component change during integration. Prove the whole native start-to-delivery flow with a real decision, interruption/recovery, and access to agents, checks, memory and Axe evidence.
