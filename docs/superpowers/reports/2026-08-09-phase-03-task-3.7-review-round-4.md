## Correction

- Every asynchronous teardown effect, residue read, settlement persistence,
  and completion handoff is coordinator-bounded; panics and waiter-channel
  failure become bounded `CleanupFailed` reports with residue.
- Handoff failure removes active state, retains a bounded completed settlement
  in memory, preserves residue even after a `Closed` report, and does not set a
  coordinator-wide failure flag.
- Caller-constructed completion observations are diagnostics-only; the
  proof-bearing `JobCompletionMessage` has no public constructor and is
  created only through the concrete completion-receiver capability.
- Batch requests reserve executor capacity and pass one full-scope atomic
  admission barrier before any branch is queued.
- Cleanup uses a fixed worker pool and a fixed 256-entry queue. The pressure
  test drives 300 concurrent exact requests and replays all of them.
- Residue falls back to the fence's canonical root executable and redacts
  key/value, separate option-value, and Authorization bearer forms while
  retaining explicit unavailable markers.
- The Windows boundary wires a real `ManagedProcessJob`, Job termination,
  completion receiver, authoritative zero query, retained handle, registry
  release, and coordinator settlement.

## Focused Luna-max correction

The critical boundary was `ProcessRegistry::drain_job_completions`: it accepted
the same public `JobCompletionMessage` type that a caller-implemented fake
could construct with `JobCompletionMessage::new(fence, ActiveProcessZero)`.

The correction removes that public constructor and separates the public
`JobCompletionObservation` path from the proof-bearing message. The
`JobMembership` drain remains receiver-owned, while only the concrete
`ManagedProcessJob` completion receiver can create a message through its
private token. Integration fakes now remain observation-only; the positive
zero-proof teardown regression drains directly from the real `ManagedProcessJob`
in `teardown_windows.rs`.
