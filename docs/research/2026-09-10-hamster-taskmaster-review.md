# Hamster Studio and Taskmaster: code and lessons for DevManager

Reviewed 2026-09-10. Incorporated as A12 in [SPEC.md](../../spec/ai-orchestration/SPEC.md), the [native UX chapter](../../spec/ai-orchestration/UX-SPEC.md), and the [autonomy review](../../spec/ai-orchestration/AUTONOMY-REVIEW.md).

## Recommendation

Take Hamster’s connected requirements, outcome measurement, contextual research, and reusable working practices into DevManager. Keep one goal conversation, the existing native shell, standard qualified coding harnesses, and the host’s durable execution authority. The strongest reusable source is the public **Hamster agent plugin**, especially its canonical worker instructions and generated adapter checks. Taskmaster is useful as a behavioral reference, but its actual license restricts commercial reuse.

This supports the direction already chosen: Robin hands over finished specs or a software problem; the lead handles the work. Hamster provides useful product and implementation examples, but the reviewed evidence does not establish a replacement that already satisfies DevManager’s entire recovery, independent verification, multi-repo, memory, and native UX contract. Product pages describe capabilities; they are not reliability measurements.

The April source must not be assumed to implement September Studio behavior.
- Hamster’s public plugin, commit `6f5862edb06c5606c00609eb7dfc938dd75047f2` dated 2026-09-09. The discovered `gethamster/cli` repository resolves to `gethamster/plugin`. Reviewed worker/ship/resume/review/retrospective protocols, packaging, generated adapters, and validation boundaries. This repository contains plugin instructions and scripts; it is not Studio’s server, context index, cloud execution backend, or the source of the distributed CLI binary.
- Twelve [isolated Taskmaster helper probes](evidence/hamster-taskmaster-review/probe-results.json) passed. PASS confirms the stated observation, including limitations. They use synthetic inputs and extracted helpers, with imports removed and registration callbacks stubbed; they do not run a model, full schema pipeline, process runner, or application. The [probe script](evidence/hamster-taskmaster-review/probe.mjs) reads external source without vendoring it.
- Two upstream read-only plugin checks passed: adapter drift checking and package validation. These validate packaging and source consistency, not client registration or execution quality. See [check output](evidence/hamster-taskmaster-review/plugin-check-results.json) and [source/archive/page provenance](evidence/hamster-taskmaster-review/sources.json). Source hashes remained unchanged.

No account, service, plugin, dependency, provider, Rust build, or installed application was started or changed. Public source was downloaded into an isolated temporary directory. No comparative delivery benchmark, cloud-agent run, native capture, or step-4 build document was produced.

The [pack integrity check](evidence/hamster-taskmaster-review/pack-check-results.json) validates local links, Markdown structure, preserved scenario/review identities, pinned source hashes, and the unchanged eleven A10 image targets. This is document/reference validation, separate from the future runtime acceptance.

## Code candidates and important differences

### Hamster plugin: selective source reuse is practical

The [root license](https://github.com/gethamster/plugin/blob/6f5862edb06c5606c00609eb7dfc938dd75047f2/LICENSE) is MIT. Its [README licensing section](https://github.com/gethamster/plugin/blob/6f5862edb06c5606c00609eb7dfc938dd75047f2/README.md#license) explicitly separates repository source from prebuilt CLI binaries supplied under commercial terms. A future source adaptation must retain the applicable notice and check exact-file provenance. Do not infer that the binary, hosted MCP service, or Studio backend shares the repository’s grant.

### Taskmaster: use the lessons and independently written acceptance cases

The pinned [LICENSE](https://github.com/eyaltoledano/claude-task-master/blob/c0c98d367c55296bfe69e65680625b6db437af02/LICENSE) adds Commons Clause restrictions to the MIT text, and [licensing guidance](https://github.com/eyaltoledano/claude-task-master/blob/c0c98d367c55296bfe69e65680625b6db437af02/docs/licensing.md) discusses competing commercial products. Treat it as a restricted source reference for this product; do not approve copying its implementation, prompts, or tests based on an “MIT” label. DevManager can implement the general behaviors independently. Actual reuse would need suitable permission/terms first.

## What A12 changes in the spec

Eight added scenarios bring the pack from 184 to **192**, retaining every prior ID:

| Scenario | Required improvement |
| --- | --- |
| N13 | Bounded research resolves a specific question, preserves cited facts versus proposals, and returns its conclusion to the owning goal/artifact. |
| G09 | Follow source → requirement/decision → plan → current evidence; changed or restored documents preserve history and invalidate affected work without rewinding external effects. |
| G10 | Validate dependency meaning, inherited prerequisites, stable identities, and required coverage during generation/repair. |
| R13 | Present a relevant registered tool set while preserving required capabilities, discovery, and actual authority. |
| M10 | Keep harness-specific context and instruction projections derived from one canonical, versioned source; detect drift and stale/offline views. |
| L11 | Reconcile delivered behavior with impacted project knowledge once per version, with coherent synthesis and truthful publication state. |
| C10 | Report the agreed outcome with its measurement conditions; completed tasks cannot prove unmeasured results or business causality. |
| U19 | Deliver these behaviors in native Plan/Checks/Knowledge/Agents and the conversation, including stale/missing-source, changed-plan, result-pending, and knowledge-update states. |

The eleven A10 reference compositions remain the baseline. A12 specifies additional content and transitions in those same surfaces; they are not newly captured native evidence. Step 4 must prepare expanded reference states where needed before coding and verify actual native interactions and appearance in each affected slice. A backend link table, a placeholder panel, or a copied Hamster page does not deliver U19.

The practical gain is better continuity from intention to evidence, reusable instructions that do not drift, and knowledge that reflects verified changes. The added maintenance cost is source lineage, projection validation, and a small set of visible states. Consolidating them into existing authority and UI avoids a separate planning platform. The remaining uncertainty is implementation reliability under real work and disruption, which the existing live acceptance workloads must establish.
